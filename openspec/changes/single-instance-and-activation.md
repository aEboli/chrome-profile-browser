# 应用单实例与重复启动激活

## 目的

让桌面应用在安装版、开发运行和调试启动之间保持同一个应用实例边界，重复启动时直接唤起已有配置中心，不创建新的 Electron 主进程。

## 行为

- 应用使用稳定的内部名称、Windows App User Model ID 和位于系统 `appData` 下的固定锁目录申请单实例锁；申请后立即恢复 Electron 原来的 `userData`，不迁移 profile 或设置数据。命令行传入不同 `--user-data-dir` 不会绕过应用级唯一性。
- 第二实例在主实例完成初始化前到达时先记录请求；配置中心创建完成后恢复并聚焦已有窗口。
- 重复启动已运行的 profile 时，主进程返回已有运行结果，并恢复、显示和聚焦已有的内置浏览器窗口；不会重复创建浏览器窗口、外部 Chromium 或代理核心。
- Chromium 的 GPU、网络服务和页面 renderer 等子进程仍按 Chromium 的多进程模型运行；它们不属于重复的应用主实例。

## 设计

- 在调用 `requestSingleInstanceLock` 前固定 Electron 应用身份，并临时将 `userData` 指向稳定锁目录；拿到锁后立即恢复启动时的原路径，让打包、开发和调试入口共享实例键且保留各自数据路径。
- 在 `ready` 之前注册 `second-instance` 监听器，用待处理标志覆盖初始化竞态；主实例准备后统一调用配置中心聚焦逻辑。
- 保留现有 `profileLaunches` 并发去重和运行状态校验，重复 profile 请求只走已有实例分支。

## 验证

1. 使用默认启动参数和带不同 `--user-data-dir` 的第二次启动，确认第二个 Electron 主进程退出，已有配置中心恢复并获得焦点。
2. 连续触发同一 profile 的启动入口，确认返回 `mode: existing`，窗口数量和代理核心数量不增加。
3. 检查 Electron 子进程命令行，确认 GPU、utility 和 renderer 子进程仍可存在，但只有一个应用主进程。
4. 运行主进程语法检查和生命周期测试。
